# VIONA 16.0 — platform release

## What works in code
- **VIONA ID 2.0:** authenticated server-backed Telegram profile, account creation date, editable nickname (separate from Telegram's verified username), saved in PostgreSQL.
- **Orders:** authenticated order requests with server-calculated prices, owner-scoped history, UUID order IDs, and initial status `created`. This is **not a payment processor**. No money is charged.
- **Notifications:** order-created and status-changed notifications generated by PostgreSQL trigger. Owner-only read and mark-read endpoints. No Telegram push or real-time socket push yet.
- **Product links:** `/product/:id` shareable SPA deep links, quick-view modal and three abstract art variations. **No actual product photo gallery** exists until images are uploaded. Per-product server-rendered SEO is not implemented.
- **Visual Engine:** new transitions, overlay, art treatments, mobile styling and reduced-motion support.
- **PWA:** install manifest, offline public shell fallback and service worker. API, authentication and order responses are never cached.
- **SEO:** canonical, Open Graph and robots metadata on the landing page.

## Required deployment steps
1. Deploy a PostgreSQL database and set **DATABASE_URL** privately in Render (the original site already supports this variable). Do not send credentials to chat or GitHub.
2. Run `migrations/016_viona_platform.sql` against that PostgreSQL database using a trusted database client or Render console. **The application does not auto-run migrations.**
3. Ensure existing Telegram environment variables are present: `TELEGRAM_BOT_TOKEN`, `SESSION_SECRET` (32+ chars), `PUBLIC_BASE_URL=https://viona.space`.
4. Merge PR to main, let Render deploy, and test `/api/v16/profile`, `/api/v16/orders`, `/api/v16/notifications` with a Telegram session.
5. Without a database/migration, these endpoints return errors. The site still shows its existing catalog, Telegram login, cart and contact form.

## Security and scope
- V16 routes require a valid signed Telegram session; users can only see/update their own profile, orders and notifications.
- State-changing requests require same-origin `Origin` and JSON content type. Order product IDs are validated and prices are calculated from the server-side catalog.
- Inputs are length-limited; SQL uses parameters; frontend escapes user-controlled text.
- **Not included:** payments, persistent cart sync, seller/admin status editing UI, order fulfilment automation, real Telegram notifications, product image hosting, per-product SSR SEO, full end-to-end browser testing.
- Avoid exposing any previously leaked Telegram token or session secret. Rotate both if compromised.

## Suggested smoke tests
1. Logged-out GET /api/v16/profile returns 401; logged-in user sees only their own data.
2. Invalid Origin POST /api/v16/orders returns 403.
3. Unknown product IDs and malformed order requests return 400.
4. Valid order returns 201 and appears in history with a new notification.
5. Different Telegram account cannot see or mark notifications belonging to another account.
6. Profile nickname update persists after reload; Telegram username remains separate.
7. PWA installs and offline public shell loads; private endpoints never load from cache.
8. Product permalink opens catalog detail; verify mobile and all five themes.
